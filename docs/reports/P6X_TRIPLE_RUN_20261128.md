# P6X：三次独立重写 + 双硬件交叉验证

> 协议：`scripts/p6x/PROTOCOL.md`
> 数据：`reclaimed/p6x_20261128/`（p6x_A/B/C.json、p6x_mc16.json、p6x_verdict.json）
> 判定脚本：`scripts/p6x/p6x_compare.py`

## 0. 结论先行

| 项 | 结果 |
|---|---|
| L1 实现一致性（三次独立重写） | **PASS**，最大相对差 **0.0151%**（判据 0.1%） |
| L1 跨硬件（BW DCU / Z100 DCU） | **PASS**，A 与 B 分处两代 DCU，中位差 0.003% |
| L2 统计稳定性（MC 4→16） | **PASS**，最大变化 4.45%，`best` 全部 ≤1.07% |
| 13 种子标定后中位 | **0.0865**（三次实现：0.086536 / 0.086533 / 0.086531） |

**由此推翻上一轮的一个结论**：P6 报告里的"目标拓扑中位 0.0843 优于官方 standard 最优 0.0853（赢 1%）"
在三次独立实现、两台硬件的口径下变成 **0.0865 vs 0.0868 —— 统计上打平，不是赢**。
官方 lite 的 0.0999 则确实被明显超越。

> 三次重写的真正价值不在"把数字算得更准"，而在下面第 4 节列出的 **8 个真实 bug**——
> 其中 3 个会让结论直接错掉，而它们在单次实验里全都不会被发现。

## 1. 为什么要这样设计

用户的判据是"三次一致才算结论"。这个判据能抓、和不能抓的东西必须分清，否则会误以为
"三次一致"等于"结论正确"：

| 层 | 能抓 | 不能抓 |
|---|---|---|
| 独立重写（L1） | 实现错误：索引错位、分组轴错、因果对齐错、量化口径错、求和维度错、设备迁移漏 | 蒙特卡洛噪声、模型假设偏差 |
| 加大 MC（L2） | 蒙特卡洛噪声是否主导结论 | 系统偏差 |
| 换硬件 | 结果是否依赖具体加速卡/数值库 | 实现逻辑错 |

**本协议不能验证的**：V_SAT∝I_TAIL 这个电路假设、ToneTwist 数据集的采集链路、
6-bit 量化是否真是目标工艺的合理抽象。这些需要电路级复核与数据文档，不是重写代码能解决的。

## 2. 硬件矩阵

| 实现 | 硬件 | 软件栈 | 说明 |
|---|---|---|---|
| A | bw2（海光 BW，gfx936） | torch 2.9.0 + DTK 26.04 | 主算力 |
| B | **z100（海光 Z100SM，17 GB）** | torch 2.1.0 + HIP 5.7 | **不同代 DCU** |
| C | bw2（不同节点） | torch 2.9.0 + DTK 26.04 | 流式执行模型 |

A 与 B 分处两代加速卡，仍一致到 0.003%——说明结论不依赖具体卡。

## 3. 三份实现的差异（刻意做得不一样）

| 环节 | A | B | C |
|---|---|---|---|
| 执行模型 | 整段一次前向 | 整段一次前向 | **流式分块**（带 RF−1 历史，只取本块） |
| 抽头取数 | 时间轴切片 | `index_select` gather | 时间轴切片 |
| 分组收缩 | `einsum` | `chunk` + 广播乘 | 逐组切片 |
| tanh | `torch.tanh` | **sigmoid 恒等式** `2σ(2z)−1` | `torch.tanh` |
| 量化 | `round(w/scale)·scale` | **码本 + searchsorted 最近邻** | reshape 视图 + round |
| 累加精度 | float32 | **float64 求和** | float32 |
| head 累加 | 原地相加 | **列表 stack 后一次性 sum** | `functools.reduce` |

流式（C）是三种里最有价值的独立点：它用完全不同的失效模式检验**因果对齐**——
若"valid 卷积 + 末尾裁剪"的口径写错，块与块接缝会出现周期性台阶，与整段实现是两种不同的错法。

三份实现的**理想路径都与官方 `nam` 包前向对拍通过**（max|Δ| 均在 3e-7 ~ 1e-6），
这是它们的共同锚点——否则"三方一致"只可能意味着"三方一起错"。

## 4. 三次重写抓到的 8 个 bug

按严重程度排序。**这条清单就是这套协议的全部价值**。

| # | 实现 | bug | 后果 | 怎么暴露的 |
|---|---|---|---|---|
| 1 | B | `conv1d_sim` 用线性矩阵乘算 Gilbert | **逐乘积非线性被破坏**，物理模型直接错 | 自查（写的过程中发现概念错） |
| 2 | C | 流式裁剪用 `e-ws`（含历史段）而非 `e-s` | 块间接缝错位；**只在长段（5 s）暴露，短段碰巧对** | 服务器 sanity 失败 → 本地按段长/分块网格复现 |
| 3 | A | 理想路径仍传 `BETA_H3=0.002` | "数字精度"其实带非线性，**数字基线全错** | 逐算子对拍发现 1e-4 级偏差 |
| 4 | A/B/C | `net` 未 `.to(DEVICE)` | 只在 DCU 上崩，本地 CPU 测不出 | z100 首次运行报 device mismatch |
| 5 | A/B/C | `nrms` 里预测在 CUDA、目标在 CPU | 同上 | z100 第二次运行报 two devices |
| 6 | A | `def seg(..., ln=SEG_LEN)` 默认参数在 def 时绑定 | `--seg-len` 被静默忽略，**用了 5 s 而不是设定的段长** | A/C 同配置差 8.5% → 追查发现是段长不同 |
| 7 | B | `torch.tensordot(dims=0)` 得到 4 维外积 | 形状错，运行时崩 | 本地冒烟 |
| 8 | A/B/C | 种子筛选 `k.startswith("s")` 把 `std` 算进种子 | 中位数被官方模型的数污染 | 打印模型清单时发现 n=14 而非 13 |

其中 **#1 #2 #3** 都会直接导致错误结论，而它们在"只做一次实验"的流程里 100% 会被漏掉：
#1 会给出"QAT 无效/有效"的错误归因，#2 会让流式结果系统性偏离，#3 会让所有"数字精度"失去意义。

#6 尤其值得记：它让 A 与 C 在同一配置下差 8.5%，看起来像"两个实现不一致"，
实际是**测试脚手架 bug**，不是数值分歧。若不追查到根因，会误判"独立实现不可信"。

## 6. L2 判定明细

| model | metric | MC=4 | MC=16 | 变化 |
|---|---|---:|---:|---:|
| s7 | free / best | 0.1082 / 0.0858 | 0.1077 / 0.0867 | 0.48% / 1.07% |
| s23 | free / best | 0.1262 / 0.0819 | 0.1208 / 0.0823 | **4.45%** / 0.47% |
| s71 | free / best | 0.1638 / 0.0848 | 0.1632 / 0.0840 | 0.37% / 0.92% |

- `best` 全部 ≤1.07%，聚合中位只动 **0.91%** → 结论量对 MC 稳定。
- `free` 在 s23 上动了 4.45%，说明**单点 free 值不可作为细粒度判据**（MC=4 下 ±5% 是正常的），
  但用它做"是否需要校准"的定性判断仍然安全（差距是 2 倍量级）。

## 7. 修正后的选型结论

| 口径 | 13 种子中位 / 官方值 | 说明 |
|---|---:|---|
| 目标拓扑 `L10-ch32-g8-bigRF`（k+V 全用上） | **0.0865** | 三次实现：0.086536 / 0.086533 / 0.086531 |
| 官方 standard（k+V 全用上） | **0.0868** | 差 0.3%，**统计上打平** |
| 官方 standard（不加手段） | 0.0906 | |
| 官方 lite（不加手段） | 0.0999 | 目标拓扑领先 13% |

**"赢 1%" 这个说法撤回。** 在三次独立实现 + 两台硬件的口径下，目标拓扑标定后与官方 standard
**没有可分辨的精度优势**；对官方 lite 有明确优势。

注意 P6X 的器件模型与 P6 的 `DevSim` 有**三处口径差异**，所以设备的绝对值比 P6 高 1~2.5%
（P6 中位 0.0843 → P6X 0.0865）。逐项列出，不做事后归因的过度解释：

| 差异 | P6 `DevSim` | P6X 协议 | 影响方向 |
|---|---|---|---|
| 偏置的失配/漂移 | **对偏置也施加** 1% 失配 + 3% 漂移 | 只对权重（dim≥2）施加，偏置不动 | P6 更悲观 |
| 热噪声注入点 | 2 处/层（激活后、layer1x1 后），共 20 个 | conv / mixer / layer1x1 / rechannel / head，共 32 个 | P6X 更悲观 |
| MC 抽样种子 | 单一生成器顺序抽（seed 1000+i） | 按名字 CRC32 定种子（与调用顺序无关） | 只换样本，不改分布 |

用 MC=16 复核后这个差距仍在（P6X s7 free 0.1077 vs P6 0.1056，差 2%），说明它不是 MC 噪声，
而是上表前两项的口径差。**两项差异都不改变任何排序**，但绝对值的跨报告比较必须以同一份口径为准。
（偏置该不该施加失配，本身是个建模选择：偏置通常由数字域或电流源给出，不经过乘法器阵列，
 P6X 的做法更贴近"失配只发生在 Gilbert 阵列里"这个物理图景。）

### 7.1 但摆幅规格可以收窄到 3 个节点

`p6b2_specs.json`（13 种子 × 6 套固定规格，k 取各子最优，V_HIGH=96）：

| 规格 | 中位 | 最差 | 收益回收率 中位 / 最小 |
|---|---:|---:|---:|
| S0 全 16 | 0.1235 | 0.2147 | 0% / 0% |
| S1 只 `head` | 0.1130 | 0.1463 | 0.3% / −25.7% |
| S2 只 `L8+L9` | 0.0913 | 0.1991 | 85.2% / −9.5% |
| **S3 `head+L8+L9`** | **0.0875** | **0.1006** | **95.8% / 71.0%** |
| S4 再加 `L5+L6` | 0.0874 | 0.1015 | 95.0% / 75.2% |
| S5 全层 | 0.0843 | 0.0974 | 100% / 100% |

- **head 单独给高摆幅完全无效（0.3%）**——因为免费的 k 重平衡已经吃掉了 head。这与 P6-B 的
  kbal 归因（head 贡献 → 0.0000）互相印证。
- **真正需要高摆幅的是 `L8` 和 `L9` 两层**，加上 head 就拿到 95.8%；再给 L5/L6 毫无收益（0.0874 vs 0.0875）。
- 代价从"全部 10 层 ×6"降到"3 个节点 ×6"：按乘法器加权，高摆幅部分从 18304 降到 3680（20%）。

## 8. 尚未按新协议重做的部分

以下结论目前仍是**单次实验**，按用户判据还不能算定论，需要各补两次独立实现：

1. P6-B 的分层预算（s7 / s71 / 官方 std 的逐 scope 归因）——只有一次。
2. P6-B2 的 6 套规格表——只有一次（但 13 个种子的横截面比单种子强）。
3. P6-A 的 QAT 训练——300 ep 已跑完，数字侧 ESR 5.0e-3（比未加噪 s7 差约 39%，
   符合"正则化会牺牲数字精度"的预期）；**器件侧尚未评估**，且必须走三次实现。
4. P6-D2 的 k×V 标定网格（12 配置版）——P6X 用的是 4 配置版，两者中位一致（0.0843 vs 0.0865 的差异
   来自噪声模型，不是网格）。
