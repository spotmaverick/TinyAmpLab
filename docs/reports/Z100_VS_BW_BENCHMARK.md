# Z100（深算一号） vs BW（深算三号）实测性能对比

> 数据源：① TinyAmpLab 训练日志（同模型/协议/数据集/300ep 的受控对比）；
> ② 2026-11-25 晚在两卡上跑的**对等 benchmark**（同脚本、MD5 一致）。
> 可复现：`arch_v2_local/*.log`、`arch_analog_local/*.log`、`runs_bw/*.log`；
> benchmark 脚本 `bench_peer.py` / `bench_conv_detail.py`，旧卡 Slurm 作业
> 49908812 / 49909201。

> **结论速览**：系统级 29×。分解为纯算力代差 **5.3×** × 软件栈/算子实现
> **8.4×**。机制是旧 torch 的长序列 dilated conv1d 访存缺陷——
> 短序列上两卡几乎同速（1.1×），dilation=512 时旧卡暴涨 3.4× 而新卡无变化。

## 一、卡型澄清

| | 旧服务器 wuzh02 | 新服务器 BW |
|---|---|---|
| 卡型 | **DCU Z100**（深算一号，C878180） | **BW**（深算三号，rocm-smi 显示 `Card Series: BW`） |
| 显存 | 17.2 GB HBM | 64 GB HBM |
| 软件栈 | DTK 22.04.1 / torch 1.10.0a0 / Python 3.8 | DTK 26.04 / torch 2.9.0+das.opt1.dtk2604 / Python 3.11 |
| 调度 | Slurm `-p wzhdtest --gres=dcu:1`，8 卡 | 无 Slurm，单卡容器，多进程并发 |
| 并发 | 每作业独占 1 卡 | 6 作业共享 1 卡 |

> 原始记录冲突。按 README/NAM_COMPARISON 统一为深算一号 Z100。

## 二、核心结果：系统级加速 29×

最干净的对照是 `full_ch12`（= 官方 lite 的同构复刻）s7，300 epoch：

| | 旧卡 Z100 | 新卡 BW（独占） |
|---|---:|---:|
| 总耗时 | **9192 s**（2.55 h） | **317 s**（5.3 min） |
| 每 epoch | 30.6 s | 1.06 s |
| 每 batch（38/ep） | 806 ms | 28 ms |
| test NRMS | 0.078476 | 0.078471 |

**加速比 = 29.0×**

另一个严格配对（同 variant/seed/epochs）是 `lite s11`：
旧卡 9187 s，新卡 753 s（但新卡当时是 4 作业并发），加速 12.2×。

## 三、这不是"跑得快但算得不同"——逐 epoch 验证

对同一作业的 16 个共同 epoch 逐点比对 loss：

| ep | 旧卡 loss | 新卡 loss | 相对差 |
|---:|---:|---:|---:|
| 0 | 0.037633 | 0.037633 | 0.00% |
| 40 | 0.001194 | 0.001195 | +0.08% |
| 120 | 0.000642 | 0.000643 | +0.16% |
| 200 | 0.000503 | 0.000503 | 0.00% |
| 299 | 0.000403 | 0.000403 | 0.00% |

16 点平均相对差 **+0.015%**，最大 0.16%。val_NRMS 也逐点对齐。
结论：**完全相同的数值路径**，29× 是纯粹的执行速度差异，没有以精度换速度。

## 四、29× 的归因：对等 benchmark 实测分解（已坐实）

旧卡并未停用。2026-11-25 晚在两卡上跑**完全相同的 benchmark 脚本**
（MD5 校验一致：`bench_peer.py` / `bench_conv_detail.py`），把归因从推断升级为实测。

### 4.1 核心分解

| 测试项 | Z100 (torch1.10/DTK22) | BW (torch2.9/DTK26) | 加速比 | 性质 |
|---|---:|---:|---:|---|
| **matmul 4000²** | 13.55 ms / 9.45 TFLOPS | 2.56 ms / 49.96 TFLOPS | **5.3×** | **纯算力代差** |
| conv20 fwd+bwd (L=196092) | 359.58 ms | 8.09 ms | **44.4×** | 算力 + 算子实现 |
| full step (fwd+mse+bwd+Adam) | 360.73 ms | 8.30 ms | **43.5×** | 端到端单步 |
| 系统级 300 epoch | 9192 s | 317 s | **29.0×** | 含启动/评测摊销 |

**分解结论**：
- 纯硬件算力代差（matmul 代理）= **5.3×**（芯片）
- conv 算子级加速 = 44.4× = 5.3 × **8.4×（软件栈/算子实现超额收益）**
- 系统级 29× 略低于单步 43.5×，因为新卡上固定开销（数据加载、eval、
  Python 主循环）占比更高，卷积本身被压到 8ms 后这些成了瓶颈

> 上一轮报告基于公开规格推断"软件栈 ~7×"，**实测为 8.4×，推断成立**。
> 但硬件差被我低估了：公开规格说带宽 ~2×，实测纯算力差 5.3×。

### 4.2 机制：为什么软件栈收益被本项目放大

对同一单层 conv 做长度扫描，得到决定性的缩放规律：

| 序列长度 L | Z100 | BW | 加速比 |
|---:|---:|---:|---:|
| 4,800 | 0.55 ms | 0.51 ms | **1.1×**（几乎相同） |
| 48,000 | 3.04 ms | 0.52 ms | 5.8× |
| 196,092 | 12.50 ms | 0.55 ms | **22.7×** |

- **Z100** 时间随长度近线性增长（α≈0.83）→ 受**显存带宽**主导
- **BW** 时间几乎不随长度变化（α≈0.02）→ 受**固定启动开销**主导，卷积本身极快

dilation 的影响更说明问题（长序列 20 层）：

| | dil=1 | dil=512 | 比值 |
|---|---:|---:|---:|
| Z100 | 252.92 ms | 852.23 ms | **3.37×**（暴涨） |
| BW | 8.36 ms | 8.04 ms | **0.96×**（无差异） |

**旧 torch 的 dilated conv1d 实现存在访存缺陷**：大 dilation 造成跳跃访存、
缓存失效，时间暴涨 3.4×。本项目是重 dilation 负载（RF=4093，20 层
dilation 最大 512），恰好踩中这个缺陷，所以软件栈收益被放大到 44×。
短序列上两卡几乎同速（1.1×）证明这不是"新卡芯片快 44 倍"。

### 4.3 可操作的选型结论

| 场景 | 该选谁 |
|---|---|
| 本项目（长序列 + 重 dilation conv） | **BW**，系统级 29×，软件栈是主因 |
| 纯矩阵乘 / 大模型 | BW，但只有 ~5×（芯片代差本身） |
| 短序列小 conv | 两卡几乎无差别，Z100 仍可用 |
| 沿用 torch 1.10 不升级 | 即使换 BW 芯片也拿不到 44× 的算子收益 |

**关键教训**：这类工作的加速不能只看芯片规格。软件栈（torch/DTK）版本
对特定算子（尤其 dilated conv）的影响可达一个数量级，超过硬件代差本身。

## 五、并发吞吐视角：单卡 BW 顶替整个 8 卡 Z100 集群

旧卡时代：8 张 Z100 并行，单作业独占 1 卡，每卡吞吐 300/9192 = 0.033 ep/s，
**8 卡集群总吞吐 ≈ 0.26 ep/s**。

新卡 BW：6 作业并发共享 1 卡，单作业降到 4.97 s/ep，
**总吞吐 = 6/4.97 ≈ 1.21 ep/s**。

**单张 BW 的吞吐 ≈ 旧 8 卡 Z100 集群的 4.6×**，而且只用了 6% 显存
（64GB 卡跑 6 个小模型仅占 6%），还有很大并发余量。

这对本项目的直接意义：
- 从"8 卡排队 3 小时"变成"1 卡并发 25 分钟"
- 全部双种子配对实验现在可以低成本补齐（此前受限于卡时，很多只有单种子）

## 六、对新实验规划的修正

此前 `submit_round3.sh` 按"8 卡并行约 3h"估算。基于实测，新估算：

| 场景 | 耗时 |
|---|---|
| 6 作业并发（单卡 BW） | ~25 min |
| 16 作业（两批并发） | ~70 min |
| 单作业独占（锚点/精修） | ~5 min |

**建议**：不再需要按"卡时稀缺"设计最小判定集，可以直接跑全因子实验
（多种子 × 多 RF 档 × 多拓扑），把统计功效从 df=1 提到 df≥4，
彻底解决第三轮审计指出的"双种子统计不显著"问题。

## 七、局限与注意事项

1. **旧卡仍可用**：benchmark 通过 Slurm 作业 49908812 / 49909201 在
   `b01r2n00` 计算节点实测，脚本与 BW 侧 MD5 一致，非历史日志推断。
   benchmark 脚本已留在两机：`nam_probe/bench_peer.py` 与 `/tmp/bench_peer.py`。
2. 29× 是特定负载（小模型 + 长序列 conv1d + 重 dilation）的加速比。
   **纯矩阵乘只有 5.3×，短序列小 conv 只有 1.1×**——不可外推到所有负载。
3. 新卡 6 并发时单作业变慢 5×（1.06→4.97 s/ep），说明 DCU 算力是分时共享，
   并发不增加总算力，只是提高利用率。若跑大模型，应改回独占。
4. matmul 作为"纯算力代理"仍含软件栈因素（BLAS 库版本），5.3× 是
   硬件+BLAS 的混合，严格芯片代差可能更小。但短序列 conv 的 1.1×
   表明在算子效率相当时，两卡实际吞吐接近，故 44× 主要由算子实现差异贡献。
